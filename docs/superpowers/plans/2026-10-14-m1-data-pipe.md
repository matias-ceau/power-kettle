# Power Kettle M1 — Data Pipe Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A working device-to-phone raw data pipe: ESP32-C3 + BMI160 firmware streaming 400 Hz IMU data over BLE, a phone web page that records it (with labelled markers) to a raw log file, a Python reader for those logs, a one-click web flasher, and a hardware build guide.

**Architecture:** Firmware is a thin C++ pipe whose pure logic (packet encoding, ring buffer, command parsing) lives in a header-only library tested natively. The phone page (plain ES modules, no build step) speaks the BLE protocol and writes a `.pkraw` log. A Python package `powerkettle` decodes packets and logs. Byte-exact golden vectors shared by C++, JS and Python tests guarantee the three agree.

**Tech Stack:** C++17, PlatformIO, Arduino-ESP32, NimBLE-Arduino 2.x, Unity (native tests); vanilla JS ES modules, Web Bluetooth, `node --test` (Node ≥ 20); Python ≥ 3.11, numpy, pytest; GitHub Actions, GitHub Pages, ESP Web Tools.

**Spec:** `docs/superpowers/specs/2026-10-14-power-kettle-design.md` (§3 hardware, §4 firmware, §8.1 hosting, §9.1 firmware tests, §11 milestone 1).

## Global Constraints

- Sensor config default: accel ±16 g, gyro ±2000 °/s, both 400 Hz; FIFO headerless accel+gyro, watermark 20 frames.
- Pins: SDA GPIO6, SCL GPIO7, INT1 GPIO3, battery ADC GPIO4 (divider 2×100 kΩ), LED GPIO8 (active low). Never use GPIO2/8/9 for peripherals.
- BLE device name `PowerKettle`. UUIDs: service `f3a10001-6c1e-4b8e-9d2a-5e7c0b4a1d00`, `imu_stream` `f3a10002-…`, `control` `f3a10003-…`, `status` `f3a10004-…` (same suffix `-6c1e-4b8e-9d2a-5e7c0b4a1d00`).
- All multi-byte protocol fields little-endian. Max 19 samples per IMU packet; fewer when the negotiated MTU is smaller: `n_max = min(19, (mtu - 3 - 8) / 12)`.
- Raw counts on the wire; no scaling in firmware or JS.
- Python package must import only stdlib + numpy (it will run in Pyodide).
- No build step for the web app; it must work when served as static files over HTTPS.
- Pin every CDN/npm dependency to an exact version.

## Protocol reference (used by Tasks 1–6)

**IMU packet** (`imu_stream`, notify): `u16 seq, u32 first_index, u8 n, u8 flags(bit0 = overflow since previous packet), n × i16[6] (ax, ay, az, gx, gy, gz)`.
Golden: seq=0x1234, first_index=1000, n=2, flags=1, samples `[1,2,3,4,5,6]`, `[-1,-2,-3,-4,-5,-6]` →
`3412e80300000201010002000300040005000600fffffefffdfffcfffbfffaff`

**Status** (`status`, read + notify 1 Hz, 28 bytes): `u8 version(=1), u8 flags(bit0 streaming, bit1 low_battery), u16 battery_mv, u16 odr_hz, u8 acc_range_g, u8 reserved, u16 gyro_range_dps, i16 temp_raw, u32 dropped_samples, u32 sample_index, u64 time_us`.
`sample_index` = index of the next sample to be produced; `time_us` = `esp_timer_get_time()` latched at the FIFO read that produced `sample_index - 1`.
Golden: version 1, flags 1, battery 3987, odr 400, acc 16, reserved 0, gyro 2000, temp −512, dropped 7, index 123456, time 9876543210 →
`0101930f90011000d00700fe0700000040e20100ea16b04c02000000`

**Control** (write): `01` start · `02` stop · `03 u16 odr_hz u8 acc_range_g u16 gyro_range_dps` set_config · `04` ping.
Golden set_config(400, 16, 2000) → `03900110d007`. Valid: odr ∈ {100, 200, 400, 800}, acc ∈ {2, 4, 8, 16}, gyro ∈ {125, 250, 500, 1000, 2000}; anything else is rejected (no state change).
`start` flushes the BMI160 FIFO and resets `seq`, `sample_index`, `dropped_samples` and the ring buffer to 0.

**Raw log `.pkraw`** (written by the phone, read by Python):
```
magic  b"PKRAW1\n"                      (7 bytes)
u32    meta_len, then meta_len bytes of UTF-8 JSON (compact, no spaces)
repeat: u8 type, f64 phone_ms, u16 len, len bytes payload
  type 1 = IMU packet bytes   type 2 = status bytes
  type 3 = marker (UTF-8 text) type 4 = event (UTF-8 compact JSON, e.g. {"e":"disconnect"})
```
`phone_ms` = `performance.timeOrigin + performance.now()`.

## Review Focus

1. `seq` (u16) wraps after ~52 min at 21 packets/s → decoders must unwrap it, not report a giant gap. (Task 2 test.)
2. BLE disconnect mid-recording → the page keeps everything captured, logs an event, reconnects into the same log, and can still save. (Task 5 test on the recorder state; Task 6 manual check.)
3. Smaller negotiated MTU → packets with n < 19 (including n = 1) must decode everywhere. (Tasks 1, 3, 4 tests.)
4. Device power-cycled mid-recording → `first_index` restarts at 0; Python must start a new run, not interleave samples. (Task 2 test.)
5. Phone screen turns off during a set → recording must not stall: the page holds a Screen Wake Lock while recording and re-acquires it on `visibilitychange`. (Task 6 manual check.)

Rules for `to_recording`:
- Unwrap `seq` (u16) per run; a new **run** starts when `first_index` goes backwards (device reset or new `start`).
- Within a run, a gap is any jump where `first_index` ≠ previous `first_index + n`.
- Runs take ranges from the latest status before the run's first packet (default 16 g / 2000 dps).

**Files:**

**Interfaces:**
- Consumes: Task 3 `pk::` library.
- Produces:
  - `class Bmi160 { bool begin(TwoWire&, uint8_t addr=0x68); bool configure(uint16_t odr_hz, uint8_t acc_g, uint16_t gyro_dps); void flush_fifo(); size_t read_frames(pk::Sample* out, size_t max); int16_t read_temp_raw(); }`
  - `class BleLink { void begin(CommandHandler); bool connected() const; size_t max_samples() const; bool send_imu(const uint8_t*, size_t); void send_status(const uint8_t*, size_t); }` where `using CommandHandler = void(*)(const pk::Command&);`
  - `uint16_t read_battery_mv();` (16 × `analogReadMilliVolts(4)` averaged, × 2) · `void led_set(LedMode)` with `enum class LedMode { Advertising, Connected, LowBattery }` (slow blink 1 Hz / solid / 5 Hz).

BMI160 register values (verify against Bosch datasheet BST-BMI160-DS000 while implementing):
- CHIP_ID 0x00 must read 0xD1. CMD 0x7E: soft reset 0xB6 (wait 100 ms), acc normal 0x11 (wait 5 ms), gyr normal 0x15 (wait 80 ms), FIFO flush 0xB0.
- ACC_CONF 0x40 = `(0b010 << 4) | odr_code` (normal filter), ACC_RANGE 0x41: 2g 0x03, 4g 0x05, 8g 0x08, 16g 0x0C.
- GYR_CONF 0x42 = `(0b10 << 4) | odr_code`, GYR_RANGE 0x43: 2000 0, 1000 1, 500 2, 250 3, 125 4.
- odr_code: 100 Hz 0x08, 200 0x09, 400 0x0A, 800 0x0B.
- FIFO_CONFIG_0 0x46 = watermark in 4-byte units = 20·12/4 = 60. FIFO_CONFIG_1 0x47 = 0xC0 (gyro + accel, headerless).
- INT_EN_1 0x51 = 0x40 (FIFO watermark). INT_OUT_CTRL 0x53 = 0x0A (INT1 output enabled, active high, push-pull). INT_MAP_1 0x56 = 0x40.
- FIFO_LENGTH 0x22–0x23 (11 bits), FIFO_DATA 0x24. TEMPERATURE 0x20–0x21.
- **Frame byte order in FIFO is gyro then accel** (gx gy gz ax ay az); `read_frames` reorders into `Sample{ax,ay,az,gx,gy,gz}`. Read in I²C chunks ≤ 120 bytes (Arduino Wire buffer is 128). If FIFO_LENGTH ≥ 1000 bytes before a read, treat it as a possible FIFO overflow: set the overflow flag on the next packet.

Main loop behaviour:
- INT1 (GPIO3, rising) ISR sets a flag; the loop also polls every 25 ms as a fallback.
- On read: push frames to `RingBuffer<1600>` (4 s); failed pushes increment `dropped` and set `overflow_pending`; advance `sample_index` by frames read; latch `time_us`.
- While connected and streaming: send a packet when ring ≥ `max_samples()` or (ring > 0 and 50 ms since last send). Pop only after `send_imu` returns true (NimBLE 2.x `notify()` returns bool); at most 4 packets per loop iteration.
- Status: notify once per second and immediately after any command; `flags` bit1 when battery < 3500 mV.
- Commands per the Protocol reference; on disconnect: stop streaming, restart advertising. `NimBLEDevice::setMTU(247)`.
- Serial log at boot: chip ID, config, MTU on connect.
